# ADR-0003: Database schema and migrations

- **Status:** accepted
- **Date:** 2026-11-05
- **Task:** `ser-p01-03` (PLAN-001 P01-03)

## Context

ARCH-001 §2 and §5 choose PostgreSQL 17+ with PostGIS and pgvector and sketch the tables. PLAN-001
P01-03 asks for those tables and indexes as migrations that can be rolled back, and §8 lists
invariants the database should enforce rather than trust callers with.

## Decision

1. **SQL-first migrations, run by node-pg-migrate 9.** Each file in `infra/migrations/` is plain
   SQL with a `-- Up Migration` and a `-- Down Migration` section, so a reviewer reads exactly what
   runs. No ORM owns the schema; whichever data layer `services/api` picks reads it. Applied
   migrations are recorded in `public.schema_migrations`; pending migrations run in one
   transaction under an advisory lock, in file order (`checkOrder`).
2. **PostgreSQL 17 with PostGIS 3, pgvector and btree_gist**, the last one for the exclusion
   constraint below. `infra/postgres/install-ubuntu.sh` installs them from apt.postgresql.org; CI
   runs that same script. The production server follows the hosting decision (`ser-p00-02`,
   `ser-p01-02`).
3. **Schema `app`, deny by default.** PUBLIC gets no access to `app` and cannot execute its
   functions. Tables and functions are granted only to the NOLOGIN group role `serendipity_app`;
   each service gets its own login role that is a member of it (`ser-p01-02`). Row-level rules per
   person (who may read whose data) belong to the consent engine (`ser-p01-05`), not this layer.
4. **Identifiers are `uuid`, generated by `gen_random_uuid()`** (UUIDv4, built into PostgreSQL 17).
   Moving to UUIDv7 later (PostgreSQL 18 `uuidv7()`, or generated by the application) changes no
   column type.
5. **Every timestamp is `timestamptz`**, stored as UTC; a test fails on any `*_at` column of
   another type.
6. **Statuses are `text` with named CHECK constraints**, not enum types, so later migrations can
   change them without rewriting types. `dates.status` lists exactly the states of the
   `@serendipity/domain` date machine; a test compares the two.
7. **No `ON DELETE CASCADE`** on personal or money data: deleting is an explicit, audited job
   (`ser-p05-06`), and legally retained payment records must not disappear with an account. The one
   cascade is `date_participants`, which is derived from `dates`.
8. **One date at a time per person, enforced by the database.** A trigger writes one
   `date_participants` row per person for every date; an exclusion constraint
   (`user_id WITH =, during WITH &&`) refuses two overlapping rows of the same person while their
   dates hold time. A date holds time from `BOTH_ACCEPTED` (before any money is asked for) until
   `REVEALED`, and in `VENUE_UNAVAILABLE` and `SAFETY_HOLD`. The trigger is `SECURITY DEFINER`
   with a fixed `search_path`, so the application role can read `date_participants` but never
   write it.
9. **The audit log is append-only.** The application role has no UPDATE, DELETE or TRUNCATE on
   `audit_events`, and a trigger refuses them for every role, the owner included. A retention purge
   needs its own reviewed migration.
10. **Idempotency lives in unique constraints:** provider callbacks `(provider, event_id)`, payment
    orders `idempotency_key` and one live order per person and date, refunds `idempotency_key`,
    booking references, and candidate pairs `(user_a, user_b, retrieval_version)` with
    `user_a < user_b` so a pair has one spelling.

## Rolling back

`npm run db:rollback` undoes the latest migration; pass a count to go further. Every down
section drops what its up section created, in reverse order. Rolling everything back drops
the `app` schema and the three extensions. It also drops the `serendipity_app` role, unless
another database in the same cluster still uses it (the role is cluster-wide). The `db` CI job
applies the migrations one at a time, rolls them back one at a time, and checks that the catalog
is back to exactly its earlier state after each step.
